# Proposed versus implemented technology choices

P technology Table8 and appendixD/Table10 are proposals; I§4.3–4.6 already records the implemented FastAPI/HTML/CSS/JavaScript architecture. Thus October retained and extended an existing substitution; it did not newly replace Streamlit. The reasons below are engineering justifications grounded in observed responsibilities, not invented contemporaneous benchmarks or proof of formal supervisor approval.

| Choice | Proposed / actual | Defensible reason and trade-off |
|---|---|---|
| Presentation |Streamlit proposed; vanilla HTML/CSS/JS implemented by interim |Explicit control over dynamic profile rows, mobile layout, translation and browser speech; stable existing interface retained. Costs include manual DOM/state/accessibility work and a separate static-server setup. No measured claim that Streamlit was slower or inherently less accessible |
| Backend |Python proposed; Python/FastAPI implemented |Keeps Python domain engines while exposing typed, testable JSON contracts for the browser and live integration. Requires CORS/API configuration and coordination rather than one Streamlit process |
| Knowledge storage |Table8 includesSQLite/CSV/JSON; appendixTable10 listsSQLite/JSON; actualCSV |CSV remains among the proposal's main-table options, is versionable and inspectable for11 curated programmes. Strict loader/ID validation improve integrity; manual schema/relationship maintenance and limited concurrent writing remain costs. No database or persistent learner store is implied |
| Data handling |Pandas suggested; standard csv/typed validation used |Current small row-based rules and joins do not require a dataframe stack. Fewer runtime dependencies, but validation must be maintained explicitly. This is not a performance experiment proving Pandas unnecessary at all scales |
| Relevance |Rule filtering/scoring and lightweight NLP/LLM assistance proposed; deterministic interim; frozen MiniLM ONNX added later |Actual pretrained NLP is used for interest relevance after formal assessment. Local CPU inference avoids a paid learner-profile API and training-data fabrication; pinned artifacts/cache/fallback aid reproduction. Model assets/dependencies, English bias and no independent quality labels remain limitations |
| Explanations/chat |Proposal mentionsLLM/NLP support; actual templated/source-grounded explanations and deterministic guided assistant |Reduces unsupported educational narration and reuses authoritative engines. No unrestricted/generative chat or faithful latent embedding attribution. This narrows the proposed mechanism, while preserving bounded FR6/FR8 outcomes; obtain supervisor acknowledgement of the interpretation rather than claiming unchanged technology |
| Voice |Speech-to-text tools proposed; browser recognition interface used |Minimal infrastructure and direct text alternative; vendor/browser/language/network behaviour is variable and native accuracy remains unverified. Local embedding inference does not make speech offline |
| Output charts |Plotly/Streamlit charts suggested; cards/statuses/source links delivered |The guidance task can present evidence without statistical plots; no chart framework was introduced merely to match a technology list. Counts/labels require source clarity and accessible rendering |

The approved aim, domains, curated data, rule authority, explanation and prototype evaluation remain intact. Pretrained deep-encoder inference is not advanced learner-outcome predictive-model development or local deep-model training. Interface translation is not advanced multilingual NLP. Proposal diagram features such as accounts/staff roles, saved activity, notifications and analytics stores are not delivered; their relationship to the concise FRs requires an explicit supervisor decision (CONTRADICTIONS_AND_LIMITS.md). Do not silently convert diagrams into either implemented features or approved exclusions.
